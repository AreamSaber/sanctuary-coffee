## 2. 项目当前技术栈

后端是 Spring Boot 3.1.6 + Java 17 项目，使用 Spring Security、JWT、MyBatis-Plus、MySQL、Redis、Druid、Knife4j。接口统一挂在 `/api` 上，核心 API 由 22 个 Controller 暴露。

前端是 Vue 3 + Vite + Pinia + Vue Router + Element Plus 项目，并使用 ECharts 做统计图表，Leaflet 做配送地图展示。路由已经覆盖用户端、后台管理、配送员任务、财务统计、运营分析等页面。

数据库脚本包含主结构和多轮迁移，已补充退款审核字段、会员权益发放日志、配送异常、订单配送方式字段、锁定库存字段。

## 5. 已实现但仍需完善的风险点

### 5.1 配送实时位置接口缺少订单归属校验

源码证据：`DeliveryController.getDeliveryPosition()` 直接调用 `positionSimulator.getCurrentPosition(orderId)`，不像配送详情和轨迹接口那样传入 `getCurrentUserId()` 做权限校验。

风险：登录用户可能通过猜测订单 ID 获取其他订单的模拟配送位置。

建议：改为先调用配送服务校验当前用户、管理员或配送员是否有权访问该订单，再返回位置。

开发进度（2026-05-03）：已修复。`DeliveryService` 新增 `assertDeliveryAccess(userId, orderId)`，`DeliveryServiceImpl` 复用原有 `validateOrderAccess`，允许管理员、订单本人、被分配配送员访问；`DeliveryController.getDeliveryPosition()` 在返回 `DeliveryPositionSimulator` 的模拟 GPS 坐标前先执行访问校验。模拟 GPS 逻辑保持不变。已补充 `DeliveryServiceImplTest` 用例覆盖订单本人可访问、无关用户被拒、被分配配送员可访问。当前环境缺少 Maven，测试代码尚未能实际运行。

### 5.2 每日统计任务不是幂等写入

源码证据：`DailyStatisticsTask` 对销售统计、商品统计、用户统计、运营汇总使用直接 `insert`；商品统计中的 `viewCount`、`cartCount` 固定为 0，运营汇总 `conversionRate` 固定为 0。

风险：定时任务重复执行会产生重复统计行，部分指标与真实埋点不一致。

建议：按日期和业务维度做 upsert 或先删后插，并接入行为表计算浏览、加购、转化率。

开发进度（2026-05-03）：已修复第一版。`DailyStatisticsTask` 改为先读取目标日期订单和用户行为，再生成销售、商品、用户活跃、运营汇总四类统计。四类统计均按表唯一维度先查旧记录，有旧记录则 `updateById`，没有旧记录才 `insert`，避免重复执行时插入重复行。商品统计的 `viewCount`、`cartCount` 改为从 `user_behavior` 中 `targetType=PRODUCT` 的 `VIEW`、`ADD_CART` 行为计算，商品集合由订单明细和商品行为共同决定；运营汇总的 `conversionRate` 改为按“发生浏览行为的用户中完成支付的用户占比”计算，不再固定为 0。已新增 `DailyStatisticsTaskTest` 覆盖既有统计行更新、新商品/新用户插入、行为指标计算和转化率计算。当前环境缺少 Maven，测试代码尚未能实际运行。

### 5.3 财务报表退款和优惠拆分不准确

源码证据：`FinancialServiceImpl.generateFinancialReport()` 先筛选 `payStatus=PAID`，再从这批订单里找 `orderStatus=REFUNDED` 计算退款；同时 `couponDeductAmount` 使用订单总 `discountAmount`，`promotionDeductAmount` 固定为 0。

风险：退款金额可能统计不到，优惠券、促销、会员、积分抵扣不能准确拆分。

建议：退款从退款表或售后表统计；订单上增加或回算促销、优惠券、积分、会员折扣字段。

开发进度（2026-05-03）：已修复第一版。`FinancialServiceImpl.generateFinancialReport()` 改为按支付时间统计已支付和已退款订单的原始实收金额，并从 `refund` 表按 `refundStatus=1`、退款时间区间统计实际退款金额，`netRevenue` 改为 `totalRevenue - totalRefund`。促销优惠通过订单明细、活动商品促销价和订单支付时间回算，并写入 `promotionDeductAmount`；由于当前订单表只持久化总优惠额，没有单独保存优惠券、积分、会员折扣和免配送费金额，`couponDeductAmount` 已调整为“非促销优惠金额”，表示总优惠额扣除促销优惠后的合计。财务报表前端标签和 CSV 导出表头已同步该口径。已新增 `FinancialServiceImplTest` 覆盖退款表统计、已退款订单收入计入、促销优惠拆分和非促销优惠合计。当前环境缺少 Maven，后端测试代码尚未能实际运行；前端 `npm run build` 已通过。

### 5.4 商品偏好中的购买转化可能低估

源码证据：`AnalyticsServiceImpl.calculateProductPreferences()` 只统计 `targetType=PRODUCT` 的行为，并把 `PAY` 行为作为购买数；但支付成功埋点更偏向订单维度。

风险：整体漏斗能统计支付用户，但商品维度购买数可能偏低。

建议：支付成功后按订单明细补充商品维度 `PAY` 行为，或商品偏好直接从订单明细计算购买数。

开发进度（2026-05-03）：已修复第一版。`AnalyticsServiceImpl.calculateProductPreferences()` 保留 `user_behavior` 中商品维度的浏览、加购统计，同时新增从已支付和已退款订单的 `order_item` 明细中按商品汇总真实购买数量与销售额。商品偏好商品集合改为“行为商品 + 已购买商品”的并集，因此即使某商品没有商品维度 `PAY` 行为，也能在已支付订单明细中反映购买数。若订单明细没有购买记录，则兼容旧的商品维度 `PAY` 行为作为回退。已新增 `AnalyticsServiceImplTest` 覆盖商品行为浏览/加购与订单明细购买数合并、无浏览但有购买的商品保留、销售额和转化率计算。当前环境缺少 Maven，后端测试代码尚未能实际运行。

### 5.5 配送自动分配没有完整绑定配送单

源码证据：`DeliveryManagementServiceImpl.autoAssignStaff(orderId, regionId)` 会选择配送员并将其标为忙碌，但需要继续确认与配送订单的绑定是否在同一服务内完成。

风险：如果只返回 staffId 而不更新配送单，会造成后台“自动分配”与实际任务状态不一致。

建议：把自动分配动作收敛到配送服务中，保证 staff 状态和 delivery_order 状态同事务更新。

开发进度（2026-05-03）：已修复。`DeliveryManagementServiceImpl.autoAssignStaff(orderId, regionId)` 仍按区域读取空闲且启用的配送员，并按 `todayOrders` 最少优先选择；选中配送员后不再直接调用 `updateStaffStatus`，而是调用 `DeliveryService.assignDelivery(orderId, staffId)`。实际配送单创建/读取、配送员绑定、配送状态改为已分配、配送员状态改为 `BUSY`、配送轨迹写入均复用 `DeliveryServiceImpl.assignDelivery()`，并在自动分配事务内完成。已新增 `DeliveryManagementServiceImplTest` 覆盖自动分配会调用配送服务绑定配送单、无可用配送员时不会绑定。当前环境缺少 Maven，后端测试代码尚未能实际运行。

### 5.6 优惠券过期与免邮券语义不完整

源码证据：`CouponServiceImpl.getUserCoupons()` 没有在查询用户券时刷新过期状态；支付侧更偏向金额抵扣，免邮券与会员免配送费的边界需要再统一。

## 7. 毕设答辩建议展示主线

建议把系统定位为“前后端分离的咖啡商城交易与运营管理系统”，不要把重点放在真实支付或真实物流平台对接上。

推荐展示顺序：

1. 管理员登录，展示 RBAC、商品、SKU、库存、促销、优惠券、会员等级、配送方式配置。
2. 普通用户登录，浏览商品，选择 SKU，加入购物车。
3. 从购物车进入订单确认页，选择地址和配送方式，查看促销、优惠券、积分、会员折扣。
4. 提交订单，完成模拟支付，展示库存锁定到扣减、积分成长值增加、配送单生成。
5. 配送员接单、开始配送、确认送达，用户查看配送轨迹和地图模拟位置。
6. 用户确认收货并评价，后台审核或隐藏评价。
7. 用户申请售后或发票，后台处理退款、发票。
8. 管理员查看统计看板、财务报表、用户行为分析。

答辩说明重点：

- 支付采用模拟实现，重点是订单、库存、优惠、积分、配送、售后的状态一致性。
- GPS 位置是模拟坐标，重点是展示配送状态和地图可视化。
